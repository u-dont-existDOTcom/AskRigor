## #354: an answer given while the final check said not ready

The server never sees which answer the user gets, so it cannot hold one back. What it can do, exactly:

1. **Step kinds.** Each next step has a kind, in the same order (`next_step_kinds`): `input_invalid`,
   `receipt_rejected`, `research`, `declaration`, `answer_draft`, `carried_state`, `second_reading`, `tool_list`
   (`apps/research-mcp/src/next-step-kinds.ts`). Every site that adds a step names its kind; helpers that only add
   steps get a push-only sink filed under one kind. The shared test assertion checks that every result has one kind
   per step.
2. **Unchecked line.** A `not_ready` result gives `unchecked_line`, worded from the kinds still open, for example
   "AskRigor's final check has not passed: research this answer needs is unfinished and some of its statements were
   not checked." The result text says an answer given before a pass ends with it. The server instructions are at
   their 2,048-character cap, so the instruction is in the result text only.
3. **Checked draft.** The finalization receipt signs the SHA-256 of the answer draft it read, trimmed as the check
   reads it (`answer`), so whoever
   holds the receipt and the answer the user saw can tell whether it was the checked one. The owner's Codex runner
   already refuses an answer that is not the checked draft.
4. **Carried status.** The carried state keeps the last check's status and the kinds it left open (`last_status`,
   `open_kinds`, optional, so older tokens still verify). The next check gives `previous_check`, and its result text
   says that an answer given after a check that did not pass went out unchecked, and that if one did, the answer says
   what changed.

## #355: comparative null sentences

`absence_claims` also covers sentences saying an option made no difference compared with another, worked as well as
another, or did no better or worse. The existing checks then apply: a direct null result or a bounded exclusion
rests on audited studies and gives the estimate and its interval in its sentence.

## #356: yes-or-no results and the safety question

- `binary_results` (required with `answer_draft`, flat fields): each group's events and total, which direction is
  better, the follow-up, and any NNT or NNH the answer gives. Exact checks: events within totals; each group's counts
  or rate shown in the quote; an NNT or NNH consistent with the counts (between the floor and the ceiling of
  1/|risk difference| until 153b asks for the ceiling), on the right side of the comparison, shown in the quote with
  its follow-up (HRP's NNTAndNNH already asks for the follow-up period).
- `safety_question` is required with `answer_draft`: true or false.
