# MAST Fresh Validation Round 3 durable VPS execution plan

## Objective

Create, prospectively freeze, execute, judge, score, and report a separate 10-family, 120-response MAST validation study. Round 2 remains immutable historical `INDETERMINATE` evidence and receives no further submissions.

## Phase 1 — implementation and deterministic freeze

1. Branch from the Round-2 frozen implementation without changing its historical commit or private artifacts.
2. Freeze the explicit ten-family cohort, `All008` limited reserve, historical exposure ledger, 10-family decision rule, source identities, and private dispatch-seed commitment.
3. Install a study-owned Xvfb, systemd-supervised Brave, watchdog, dedicated profile, loopback CDP endpoint, and one-tab Playwright transport on `srv1894948`.
4. Require exact source/destination/composer identity, visible model/effort/session proof, an append-only send-intent and `SENT` receipt, and exact-message post-Send recovery with no automatic resend.
5. Run focused hostile tests, typecheck, build, repository governance, hash checks, and the full deterministic gate once at the freeze checkpoint.
6. Commit, push, open the Round-3 freeze pull request, and require its checks to pass.
7. Seal the private freeze receipt against the exact commit/tree, CI receipt, source identities, preregistration, environment, family manifest, and seed commitment.

## Phase 2 — live durability acceptance

1. Transfer/install only the hash-bound runtime and verify installed unit, wrapper, transport, service, process-command-line, profile, and CDP identities.
2. Execute one small non-MAST temporary/unpersonalized GPT-5.6 Sol Extra High synthetic submission.
3. Kill the browser process after its `SENT` receipt, require systemd restart, reconnect, locate exactly one full-text-hash-matching user message, recover the existing assistant response without resend, and seal it.
4. Stop before benchmark response 1 if any acceptance assertion fails. Any implementation change requires a new freeze commit, green CI, and repeated acceptance.

## Phase 3 — generation

1. Prepare and transfer all 120 private packets once with source and destination SHA-256 equality.
2. Generate sequentially through the dedicated browser and one managed content tab.
3. Verify frozen runtime and complete source/destination/composer/model/session state before every Send.
4. Resume sealed successes only. A post-Send disconnect invokes exact existing-submission recovery; zero or multiple candidates stop the study as `INDETERMINATE`.

## Phase 4 — blinded evaluation

1. Seal generation at 120/120, build opaque packets and a sealed condition map, and keep arm/protocol/result identity from judges.
2. Run independent J1 and J2 passes with GPT-5.6 Sol Extra High; preserve every raw capture.
3. Detect score-vector disagreements mechanically and run Latest Pro 5/5 J3 only for those entries.
4. Never rerun a sealed judgment; preserve malformed bytes and structured failure receipts under the attempt ceiling.

## Phase 5 — unblind, score, and report

1. Require complete J1/J2 and triggered J3 coverage before explicit unblinding.
2. Join only by opaque identifiers and bound output hashes.
3. Apply the frozen 10-family P1–P5 rule with exact rational arithmetic and equal 30-response B/D denominators.
4. Keep raw benchmark conformity, clinical validity, benchmark-target conflicts, and interpretive materiality separate.
5. Emit family, aggregate, integrity, failure, exposure, unblind, machine-summary, and final-report artifacts.

## Terminal boundaries

After response 1, any material frozen-component drift invalidates the study. Any unresolved post-Send ambiguity stops all later submissions and produces `INDETERMINATE`. A PASS remains bounded validation, not general proof of clinical superiority, and `All008` is not a broad confirmation cohort.
